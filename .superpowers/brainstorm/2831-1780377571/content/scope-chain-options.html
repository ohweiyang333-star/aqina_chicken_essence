Aqina Offer Reset: choose the build scope

The core decision is which sales/API chain should be true after this project. Pick the option that matches the business goal.

A. WhatsApp-first marketplace page
Ad traffic -> Product page
Marketplace-style product block: gallery, 1 box, 2 boxes, gift selector
WhatsApp prefill -> human/chatbot confirms order -> PayNow link/session
Admin inbox + chatbot runtime already aligned to new offer

A. WhatsApp-first

Fastest and commercially safest. Page explains the offer, every CTA opens WhatsApp/Messenger, and payment/order stays inside the existing chat/admin flow. Less risk of hardcoding checkout mistakes.

B. Page checkout + receipt upload
Ad traffic -> Product page
Variant selector: pack1 SGD47.90, pack2 SGD79.80, gift only on pack2
/api/v1/orders/with-receipt creates order + payment + customer + CAPI event
Admin orders verifies receipt manually

B. Page checkout

More complete ecommerce path, but it requires updating frontend products, checkout modal, order API package source, shipping math, tests, and browser QA. Stronger API verification needed.

C. Full offer reset chain
Ad -> Page -> WhatsApp/Messenger -> Chatbot -> Checkout -> PayNow -> Admin
New marketplace page replaces live default entry
Frontend products, static copy, chatbot media, backend order packages all share 1-box / 2-box truth
All old 4/6-box and free-delivery language removed from active customer path
Local tests + desktop/mobile browser + selected API smoke checks

C. Full reset

Best long-term consistency. Highest scope: landing page, checkout/order API, WhatsApp links, chatbot settings/media references, active routes, tests, and release verification.

Known current mismatch

The chatbot runtime has moved to the new offer, but active landing/order code still contains old pack4/pack6, SGD75/149/219, and free-delivery logic. If the project goal is a real offer reset, the API chain needs to include order/checkout, not just page copy.
